# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo layout

Two separate apps, each with own `package.json`, share the same rendering approach (marked + highlight.js) but no shared code:

- **Root** (`src/`) — the VS Code extension (`md-reader`), the primary project.
- `windows-app/` — Electron + Vite port for Windows desktop.

Work in root `src/` unless task explicitly targets windows-app.

## Documentation rule

Every change that alters behaviour, settings, commands, the message protocol, the theme file format or the architecture must update the matching docs **in the same commit/PR** — a change is not done until its docs are:

- `README.md` — user-facing features, settings table, commands table.
- `CHANGELOG.md` — an entry under the new version (Added / Changed / Fixed), dated.
- `CLAUDE.md` — architecture, settings, message protocol, rules.
- `docs/roadmap/ROADMAP.md` — status table, and mark phases/steps done or re-ordered when plans change.
- `package.json` + `package-lock.json` version, when a release is being prepared (`npm test` fails if these and the top `CHANGELOG.md` entry disagree; pending work goes under `## [Unreleased]`).
- `docs/RELEASING.md` — when the release process changes.
- `docs/THEME-FORMAT.md` — when the theme or layout file format, the colour list or the layout spec changes.

Check these before opening a PR; if a doc needs no change, that is fine, but decide deliberately.

## Commands (VS Code extension, root)

- `npm run build` — `copy-assets` then bundle extension via esbuild → `out/extension.js` (what `vscode:prepublish` runs).
- `npm run copy-assets` — copies mermaid's browser bundle + KaTeX's CSS/fonts from `node_modules` into `src/webview/vendor/` (gitignored, regenerated on every build — see `scripts/copy-vendor-assets.js`). Run this (or `npm run build`) after a fresh clone/`npm install`, or `reader.js`'s mermaid lazy-load and the KaTeX `<link>` in `buildShell` will 404.
- `npm run watch` — esbuild in watch mode.
- `npm run compile` — `tsc -p ./ --noEmit`, a pure type-check (it deliberately emits nothing, so it can never overwrite the esbuild bundle `out/extension.js`). Covers `src/**/*.ts` only; `src/webview/reader.js` is plain JS and is **never** type-checked or bundled by anything — it ships as-is and is only exercised by actually opening a panel (or, for logic, by tests that read its source).
- `npm test` — `scripts/run-tests.js`: bundles the pure modules (`src/themes.ts`, `src/starterThemes.ts`) with esbuild into `out/test-build/`, then runs every `test/*.test.js` with Node's built-in runner (`node --test`; no test framework dependency). Tests cannot import anything that needs `vscode`, so logic that should be tested must live in `vscode`-free modules (as `themes.ts` does). The suite also guards cross-file consistency: every highlight.js class has a CSS rule, `package.json` ↔ `configManager.ts` settings agree and are all read (`KNOWN_UNUSED` in `test/project.test.js` lists known-dead settings — it may only shrink), commands are declared and registered, starter themes meet contrast thresholds, and `package.json`/lock/`CHANGELOG.md` versions agree. UI behaviour still needs F5 in the Extension Development Host.
- CI (`.github/workflows/ci.yml`) runs compile + test + build + `vsce package` on every PR (Linux and Windows). **A PR should not be merged red.** Releases: push a `vX.Y.Z` tag — see `docs/RELEASING.md` (draft release, Marketplace + Open VSX publish when tokens exist, pre-release tags for hyphenated versions).
- Debug: F5 in VS Code (uses `.vscode/launch.json`) launches Extension Development Host.
- Package: `vsce package` (devDependency `@vscode/vsce`) produces the `.vsix`.

No lint script configured.

### windows-app

- `cd windows-app && npm run dev` / `npm run build` (tsc + vite build + electron-builder → nsis installer).

It has its own `node_modules` and lags the extension: it uses `marked-gfm-heading-id` and has no katex, mermaid, `marked-footnote`, or `github-slugger`. Don't assume feature parity or port code between the two by copy-paste.

## Architecture (VS Code extension)

Flow: `extension.ts` registers commands/events → delegates to `PanelManager` → webview panel runs `src/webview/reader.js` + `reader.css`, communicating with the extension host via `postMessage`.

- **`src/extension.ts`** — activation entry point. Registers all `mdReader.*` commands. `mdReader.open`/`openNewColumn` take an optional resource URI (Explorer / editor-tab / editor context menus pass it; Explorer also passes the multi-selection) and fall back to the active Markdown editor, then a file picker (`resolveTargets`) — **the reader never requires an open editor**. Auto-refresh: `onDidSaveTextDocument` and `onDidChangeTextDocument` filtered to `!document.isDirty` (a VS Code reload of an open buffer after an external change) both call `PanelManager.refreshDebounced`, alongside `PanelManager`'s own per-panel file watcher; `onDidChangeConfiguration` does the live config broadcast. There is deliberately **no** `onDidCloseTextDocument` handler: panels outlive their editor tab (a test guards this).
- **`src/panelManager.ts`** — owns all webview panels, keyed by document URI string in a `Map`. **Everything works from a `vscode.Uri`, not a `TextDocument`** (a TextDocument handle goes stale when VS Code releases a closed document): `readText(uri)` returns the text — an open editor's *dirty* buffer wins, otherwise the file is read from disk via `workspace.fs` and decoded by the pure `src/textDecode.ts` (UTF-8/BOM; UTF-16 or invalid UTF-8 falls back to `openTextDocument`), and `undefined` (e.g. file deleted) means "keep the last render". `watchFile()` gives each panel a `FileSystemWatcher` on its file's folder (pattern `*`, filtered by path in the handler because file names can contain glob characters), honouring `mdReader.autoRefresh`; `refreshDebounced()` (150 ms) coalesces watcher + save + change events into one re-render, while manual refresh is immediate. `toggleTask` re-opens the document by URI and **saves** after the edit when no editor had the file open (otherwise the edit would be an invisible unsaved buffer). Key responsibilities:
  - `open()` creates a `WebviewPanel`, builds its HTML shell (`buildShell`, inlined string containing the settings drawer/TOC overlay/find bar/shortcuts-help overlay/progress bar markup), sends initial rendered content, and wires the panel's `onDidReceiveMessage` handler (`scroll` messages for editor↔reader sync, `updateSetting` messages that mutate config via `ConfigManager`, gated by `SETTABLE_KEYS`).
  - Two-way scroll sync: reader→editor via `syncEditorScroll` (with a per-URI `ignoreEditorScrollUntil` debounce map to prevent echo loops), editor→reader via `setupScrollSync` listening to `onDidChangeTextEditorVisibleRanges`.
  - `activeUri` tracks the focused panel so toolbar commands (toggle TOC/settings/find, refresh, export) target the right one.
  - `exportActiveAsHtml()` re-renders the active document and writes a standalone .html (`reader.css` + KaTeX's CSS inlined, local images base64-inlined by default via `mdReader.export.embedImages`, mermaid — if present — loaded from a CDN rather than inlining the vendored bundle). PDF export (`mdReader.exportPdf`) has no dedicated method here — it just posts `{type:'print'}` and lets the webview's `window.print()` + `reader.css`'s `@media print` rules do the work.
  - Content security policy is nonce-based; webview only loads `reader.css`/`reader.js` from `src/webview/` plus the source document's directory (and, if `mdReader.customCssPath` is set and exists, that file's own directory) as `localResourceRoots`.
  - `mdReader.customCssPath`, if set, is checked and its `<link>` baked into `buildShell`'s HTML (after `reader.css`/KaTeX's CSS, so it wins the cascade) at panel-creation time only — `localResourceRoots` can't be changed after a panel is created, so a change to this setting takes effect on the next panel open, not live.
- **`src/themes.ts`** — pure (no `vscode` import) custom-theme model: `THEME_TOKENS` (the 24 themeable colours — 14 page + 10 `hl*` syntax — each mapping to the `reader.css` custom properties it drives; the `hl*` ones are optional in a theme), colour/id validation (`isValidColor` allows only hex/`rgb()`/`hsl()` — never `url()`/`var()`), `sanitizeThemes`, the export/import file format (`{mdReaderTheme: 2, themes: [...]}`; v2 writes **grouped** colours — `COLOR_GROUPS`: `surfaces.page`, `ink.primary`, `code.blockBackground`, … — plus optional `version`/`category`; v1 flat files are still read. In memory, in settings and on the wire themes stay **flat**: `flattenColors`/`groupColors` translate only at the file boundary, so saved themes and older extension versions are unaffected, and both shapes are accepted everywhere), `resolveCodeTheme`/`codeThemeFor` (syntax-palette validation and the export-time polarity fallback), and `lookupTheme`/`resolveThemeValue`/`effectiveBase`/`themeCss` helpers (all take the user's `custom` themes plus the loaded `starters`). A custom theme = a `base` built-in theme + only the colours the user changed, so new tokens added in later releases fall back to the base. **The token list must be kept in sync with the `colors` properties of the `mdReader.customThemes` schema in `package.json`.**
- **`src/starterThemes.ts` + `themes/`** — starter themes are *data*, not code: each `themes/*.mdtheme.json` is a normal theme file (identical to an Export, optional `author`), loaded once at activation by `loadStarterThemes()` through the same `parseThemeFile` validation as Import, and held in `ConfigManager.starters`. They are selected as `theme: "starter:<id>"`, read-only, and never copied into settings automatically (no consent-less writes to `settings.json`, and a later release can fix/add starters without touching saved data); `ThemeManager.addStarters()` copies them into the user's themes on request. To add one, drop a file in `themes/` — nothing else to register (it must pass `sanitizeTheme`, and `themes/` is packaged because `.vscodeignore` doesn't exclude it). Keep text/link/code contrast at WCAG AA or better.
- **`src/layouts.ts` + `src/layoutLoader.ts` + `layouts/`** — layouts are the typography axis, independent of the colour theme (any theme × any layout; selected by `mdReader.layout`, resolved to `standard` if unknown). Pure `layouts.ts` holds `LAYOUT_SPEC` (every value's file path, CSS variable, unit and valid range), `sanitizeLayout`/`parseLayoutFile` (out-of-range or non-numeric values and unsafe fonts are dropped — a layout file can't inject CSS), `layoutVars`, `layoutsForWebview` and `layoutCss` (export). Each `layouts/*.mdlayout.json` is data loaded at activation into `ConfigManager.layouts`; the webview receives `{id: {label, vars}}` and sets the variables inline on `<html>` (`applyLayout`), removing the previous layout's first. **`reader.css` `:root` holds the defaults and `layouts/standard.mdlayout.json` must mirror them exactly** (tests enforce this, and that every spec variable is declared and used). Layouts deliberately do **not** touch body font, size, line height or width — those stay the user's settings. Adding a layout = a file in `layouts/` + its id in the `mdReader.layout` enum in `package.json` (a test checks the two agree). Formats are documented in `docs/THEME-FORMAT.md`.
- **`src/themeManager.ts`** — `ThemeManager`: save/delete a theme (webview payloads are re-validated here, never trusted), export, import (one Replace/Keep both/Skip prompt for all conflicts), and delete-all (offers an export first; a cancelled export aborts). Themes are persisted **only** in the `mdReader.customThemes` user setting — deliberately not in `globalState`/`globalStorage`/the extension folder: settings survive updates, `.vsix`-over-the-top installs, uninstall/reinstall, and publisher/extension-ID changes (which orphan `globalState`). Never move theme storage elsewhere.
- **`src/configManager.ts`** — thin wrapper over `vscode.workspace.getConfiguration('mdReader')`. All settings are read fresh (no caching) and always written with `ConfigurationTarget.Global`. This is the single source of truth for the `ReaderConfig` shape and the `Theme`/`ReadingWidth` union types. `get()` also sanitises `customThemes` and resolves a `theme` pointing at a deleted custom theme to `auto`; `getSavedThemes()` reads only the Global-level value. A generic `set<K extends keyof ReaderConfig>(key, value)` replaces per-field setters; `get()` loops over a `DEFAULTS: ReaderConfig` object instead of one `.get()` call per field; `SETTABLE_KEYS` whitelists which fields the webview may write back via `updateSetting`.
- **`src/markdownRenderer.ts`** — wraps `marked` with a custom renderer: code blocks get highlight.js syntax highlighting + a copy button + language label (except ` ```mermaid ` fences — those render as `<pre class="mermaid">` for the webview's lazy-loaded mermaid.js to pick up, and set `hasMermaid: true` on the returned `RenderedDocument`), images become lazy-loaded `<figure>`s, tables get a scroll wrapper, blockquotes get a class, headings get GitHub-style anchor ids (via a module-scoped `github-slugger` instance) and feed a TOC array (`{level, text, id}`, levels 1-3 only) alongside the rendered HTML. Also registers two `marked` `TokenizerAndRendererExtension`s (`blockMathExtension`/`inlineMathExtension`, `$$...$$` and `$...$`) that render math to HTML host-side via `katex.renderToString()` — invalid syntax falls back to an escaped `.katex-error` span rather than throwing — and the `marked-footnote` package (GFM `[^1]` footnotes, applied via `marked.use()` since it's a full extension bundle, not a single tokenizer/renderer pair). A leading `---` YAML front matter block is handled by `extractFrontMatter()`/`parseSimpleYaml()` (a deliberately minimal scalars-and-simple-lists reader, no dependency) before the rest even reaches `marked` — `mdReader.frontMatter` (`card`/`hide`/`raw`, default `card`) controls whether it becomes a metadata card, is stripped, or is shown as an ordinary yaml code block; unrecognizable front matter is dropped rather than mis-rendered, falling back to marked's native `---` → `<hr>` handling. `renderMarkdown()` also runs `countWords()` over the raw markdown source (not the rendered HTML) to get `wordCount` — code/inline-code/math are stripped first so they aren't counted as "reading" text; the webview turns this into an estimated reading time using the configurable `mdReader.readingSpeed`. `html`, `toc`, `hasMermaid`, and `wordCount` are all sent to the webview together in one `update` message. Uses a single module-level `Marked` instance configured once at import time — never re-configure `marked`/call `.use()` inside `renderMarkdown()`, since extensions stack additively and never un-register.
- **Syntax highlighting** — `markdownRenderer.ts` runs highlight.js, which emits only `hljs-*` classes; **all colours live in `reader.css`** as `--hl-*` variables (defaults = github-dark), with `[data-code-theme="…"]` blocks for the five `mdReader.codeTheme` palettes and one rule per token class. A theme's `hl*` colours are set inline on `<html>`, which beats the palette. No highlight.js stylesheet is shipped or loaded. `reader.js` `applyCodeTheme()` sets `data-code-theme` and swaps to the matching GitHub palette when the palette's light/dark polarity doesn't match the effective `--pre-bg` (`codeThemeFor` does the same at export time).
- **`src/webview/reader.js` + `reader.css`** — the panel-side runtime (plain JS/CSS, no framework). Handles applying config (theme/font/width/etc.) to the DOM, rendering the settings drawer, TOC overlay interactions, scroll-position reporting, reading-progress bar, find-in-document (CSS Custom Highlight API, no DOM mutation — see `openFindBar`/`runFind` in `reader.js`), the keyboard-shortcuts help overlay, the reading-mode keyboard map (`j`/`k`/`space`/`g`/`G`/`n`/`p`/`t`/`s`/`?`, all skipped while focus is in an `input`/`select`/`textarea`), and lazily loading+running mermaid.js (`ensureMermaidLoaded`/`renderMermaidDiagrams`) when an `update` message says `hasMermaid`.
- **`src/webview/vendor/`** — generated (gitignored) by `npm run copy-assets` (part of `npm run build`), never edited or committed directly: `mermaid.min.js` (mermaid's browser bundle — lazy-loaded client-side, see above) and `katex/katex.min.css` + `katex/fonts/` (KaTeX's stylesheet only — math itself renders to plain HTML host-side, so the webview never loads KaTeX's JS). See `scripts/copy-vendor-assets.js`.

### Adding a new setting

Touches four places in lockstep: `package.json` (`contributes.configuration.properties`), `configManager.ts` (`ReaderConfig` interface + one `DEFAULTS` entry, plus a `SETTABLE_KEYS` entry if the webview can write it), `panelManager.ts` (settings-drawer HTML in `buildShell` — the `updateSetting` dispatch itself is generic, no switch case needed), and `reader.js` (apply the setting to the DOM + wire up the control).

### Extension ↔ webview message protocol

Extension → webview: `{type: 'update', html, toc, hasMermaid, fileName, wordCount, themeTokens, starters, layouts, config}`, `{type: 'config', config}` (live setting broadcast), `{type: 'scrollTo', percentage}`, `{type: 'toggleTOC'}`, `{type: 'toggleSettings'}`, `{type: 'find'}` (focuses/opens the find bar — triggered by the `mdReader.find` command, Ctrl/Cmd+F), `{type: 'toggleShortcuts'}` (opens/closes the keyboard-shortcuts help overlay — triggered by the `mdReader.showShortcuts` command/toolbar `$(question)` icon; the same overlay the in-panel `?` key toggles directly), `{type: 'print'}` (closes any open overlay, then `window.print()` — triggered by `mdReader.exportPdf`; the reader's own `@media print` rules in reader.css hide chrome/force light colors for the resulting PDF/printout).
Webview → extension: `{type: 'scroll', percentage}`, `{type: 'updateSetting', key, value}` (key must be in `SETTABLE_KEYS`), `{type: 'saveTheme', id?, label, base, colors}` / `{type: 'deleteTheme', id}` / `{type: 'themeCommand', id: 'exportTheme'|'exportThemes'|'importThemes'|'addStarterThemes', themeId?}` (theme editor in the settings drawer; `customThemes` is intentionally NOT in `SETTABLE_KEYS` — it goes through these validated messages, not generic `updateSetting`), `{type: 'toggleTask', index, checked}` (a task-list checkbox click — `index` matches its `data-task-index`, see `panelManager.ts` `toggleTask()`), `{type: 'openLink', href}` (a content link click other than a bare `#fragment`, which the webview handles locally — see `panelManager.ts` `openLink()`).
